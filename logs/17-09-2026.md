### 2. **Architectural Approach Definition: Hybrid Hardware-Software Co-Design**
- **Rejected** the "module-by-module" approach (build each block separately, integrate at the end) because it leads to interface mismatches and integration nightmares.
- **Rejected** the "full system in C first" approach because HLS has strict limitations (no dynamic memory, no recursion, no complex C++ objects).
- **Adopted** the **Hybrid Hardware-Software Co-Design** approach:
  1. Write the full receiver in HLS-friendly C (structs, arrays, no classes)
  2. Profile to identify bottlenecks (correlator = 90% of CPU time)
  3. Convert critical blocks to HLS (correlator, acquisition, tracking)
  4. Keep non-critical blocks in software (nav decoding, PVT solver on ARM CPU)
- This is the exact approach used by AMD/Xilinx, Intel, and Qualcomm in professional teams.

### 3. **Multi-Band Processing Roadmap Integration**
- Defined the complexity of multi-band processing:
  - **GPS L1 C/A:** 1.023 Mcps chip rate, 1023 chips (✅ Done)
  - **GPS L2C:** 1.023 Mcps chip rate, 10230 chips (CM) + 1023000 chips (CL)
  - **GPS L5:** 10.23 Mcps chip rate, 10230 chips (10x faster than L1!)

- **Key insight:** Multi-band isn't just "copy the correlator 5 times." Each band requires different code generators, sampling rates, IF frequencies, tracking parameters, and significantly more DSP resources (20-40 DSPs total).

## 🔍 Technical Explanation: Why This Approach is Correct

### **The Hybrid HW-SW Co-Design Advantage**
This approach mirrors what professional FPGA teams do at AMD/Xilinx, Intel, and Qualcomm:

1. **System Architecture in C:** Write the full receiver in HLS-friendly C from day one. This ensures all blocks have compatible interfaces and the data flow is designed as a pipeline.

2. **Profile to Identify Bottlenecks:** Not all blocks need hardware acceleration. The correlator is the bottleneck (90% of CPU time), so that's where we focus HLS effort. Navigation decoding runs once per satellite and doesn't need to be in hardware.

3. **Convert Critical Blocks to HLS:** Only the blocks that are computationally intensive and have regular, predictable data access patterns benefit from hardware acceleration. The correlator, acquisition engine, and tracking loops fit this profile.

4. **Keep Non-Critical Blocks in Software:** Blocks that run infrequently or have irregular control flow (nav decoding, PVT solver) stay on the ARM CPU. This saves FPGA resources and reduces design complexity.

### **Why Multi-Band is Significantly Harder**
Multi-band processing isn't just "copy the correlator N times." Each band has:
- **Different chip rates:** L5 is 10x faster than L1/L2, requiring 10x more DSP resources or clever time-multiplexing
- **Different code lengths:** L2C uses 10230-chip CM codes and 1023000-chip CL codes (vs. 1023 for L1)
- **Different modulation schemes:** Galileo uses C-Boc and AltBOC, which require different correlator architectures
- **Different IF frequencies:** Each band requires different RF front-end configuration and digital down-conversion
- **More DSP resources:** A triple-band receiver needs 20-40 DSP slices (vs. 4 for single-band)

This is why the timeline is realistic: we're not just duplicating code, we're building fundamentally different hardware for each band.

## 📊 Resource Estimation for Multi-Band

| Band | DSP Slices | BRAM | LUT | FF | Complexity |
|------|-----------|------|-----|----|-----------|
| GPS L1 C/A | 4 | 2 | 2501 | 3273 | ✅ Done |
| GPS L2C | 4-6 | 4-6 | 3000-4000 | 4000-5000 | 🟡 Medium |
| GPS L5 | 8-12 | 6-8 | 4000-6000 | 5000-7000 | 🔴 High (10x chip rate) |
| **Total (Triple-Band)** | **16-22** | **12-16** | **9500-12500** | **12273-15273** | **~5-7% of Zynq-7020** |

The Zynq-7020 has 220 DSPs, 280 BRAMs, 53200 LUTs, and 106400 FFs, so a triple-band receiver is well within resource limits, leaving plenty of room for tracking loops and additional channels.
